# 第 5 章 候選規則與演練（組織圖：目標如何抵達代理）

來源：page_0021～page_0023

## (a) 規則候選

### R05-1 派工時把「目的鏈」一起交給子代理

- **規則一句話**：每次派子代理，prompt 除了任務本身，還要寫出它屬於哪個專案、服務哪個最終目標（使命—專案—任務）。
- **Why**：本章「使命—專案—代理—任務」世系：代理拿到的不只是任務，還有出處，因此能做出更合理的決定，而不是盲目處理孤立指令；「目的不是靠假設，而是被交付的」。
- **How to apply**：主 Claude 的交接單第一句寫「最終目標」，第二句寫「本單位在其中的角色」，再寫輸入／完成定義／限制／回報格式。

### R05-2 角色要寫成明確的職務說明（SKILL.md／agent 定義）

- **規則一句話**：建立新的子代理或 skill 時，職責、能力範圍、對整體的貢獻與「不該做」都要寫清楚，不留含糊。
- **Why**：本章說代理職責常寫在 SKILL.md，「角色描述得好得到可用的員工，含糊就得到含糊的瞎忙」。
- **How to apply**：Claude 新建 skill 或 `.claude/agents/*.md` 時，必含「該做／不該做／觸發／不觸發／與上層目標的關係」，並用 skill-creator 的檢核流程審一次。

### R05-3 層級不超過任務所需

- **規則一句話**：能一個代理做完的事不拆成多層；只有確實有多個獨立面向時才設主管—執行者結構。
- **Why**：本章「注意」：別給代理超過任務所需的層級；迷思檢查也指出，對可預測的固定流程，固定順序往往更穩健也更便宜。
- **How to apply**：主 Claude 切分前先問「這是可預測的固定流程嗎？」——是，就用單一代理或固定腳本；否（開放目標）才用多層委派。

### R05-4 委派不免除檢查：拆解結果先過人或驗證代理

- **規則一句話**：由代理（含主 Claude）把大目標拆成子任務後，拆解本身也要被檢查，不能只檢查最底層產出。
- **Why**：本章指出 CEO 代理拆錯目標時，錯誤會沿整條鏈往下傳播且無人察覺，因為每個代理只處理自己那一片；「委派免除的是動手，不是檢查」。
- **How to apply**：大工作（預估 > 30 分鐘或多單位）在派工前，把拆解清單用一句話回報使用者；範圍有疑義時先問再派。

## (b) 演練候選

### D05-1 畫出自己的「使命—專案—代理—任務」鏈

- 步驟：挑一個自己的實際目標（例：「求職拿到 AMR 工程師 offer」），寫成 Markdown 樹：1 個使命 → 2～3 個專案 → 每專案 1 個負責代理（角色名）→ 每代理 2～3 個任務。對每個最底層任務往上追，確認能說出「因為它服務哪個專案、哪個使命」。
- 預期結果：找出至少一個追不上去的「瞎忙任務」，刪掉或改掛到正確專案下。

### D05-2 用 claude -p 模擬 CEO 拆解並人工驗收

- 步驟：`claude -p "你是 CEO 代理。目標：<開放目標>。拆成 3 個專案、每個 2 個任務，每個任務註明服務哪個專案。只輸出 Markdown。" > plan.md`；再自己逐項檢查有沒有拆錯、重複或無意義的任務。
- 預期結果：親眼看到拆解可能出錯（例：任務與目標無關），體會「錯誤會往下傳播，品質檢查留在人手上」。（走 Max 訂閱的 claude -p，不需 API 金鑰。）
