# 第 6 章 候選規則與演練（心跳、例行與排程）

來源：page_0024～page_0026

## (a) 規則候選

### R06-1 排程頻率「必要時才頻繁，能少就少」

- **規則一句話**：替使用者設定 cron、systemd timer、雲端排程或 /loop 時，先問「真正需要多快的反應？」，預設選最慢可接受的節奏。
- **Why**：本章「聰明安排例行節奏」：較慢的節拍幾乎總是比較好，每多一次心跳就是一次可能的模型呼叫與成本點，代理一多就成倍放大，緊湊節奏很少帶來更好產出。
- **How to apply**：Claude 建排程前在回報中寫出「選這個頻率的理由＋每月預估執行次數」；遇到 ≤ 15 分鐘的頻率且會呼叫 LLM 時，主動建議放慢。

### R06-2 心跳是「檢查邀請」，沒事就不呼叫模型

- **規則一句話**：定期執行的代理流程，第一步先用便宜的方式（檔案、API、git 狀態）判斷有沒有新事，沒有就直接結束，不呼叫 LLM。
- **Why**：本章「心跳不是行動命令，而是檢查邀請」；迷思檢查也提醒「沒事時心跳不花錢」是錯的，光是檢查都可能是一次模型呼叫，只有懂得節省的代理才能避免。
- **How to apply**：Claude 寫排程腳本時，在呼叫 `claude -p` 前加「有無新輸入」的前置判斷（例：比對上次處理的時間戳或檔案雜湊），無變化就 exit 0 並寫一行 log。

### R06-3 防失控迴圈：同一動作重試設上限

- **規則一句話**：自動流程中同一動作連續失敗或無進展 3 次就停止並通知，不無限重試。
- **Why**：本章的「失控迴圈（runaway loop）」：代理每次心跳都觸發昂貴動作卻沒結論，就會一再嘗試、一再花錢、毫無進展，是這類系統最大的實務痛點。
- **How to apply**：Claude 撰寫的長時程／排程腳本內建重試計數與進度檢查；與主管代理守則的「同一錯誤連續 3 次就停止並回報」一致。

### R06-4 webhook 入口先上鎖再啟用

- **規則一句話**：建立任何可由外部觸發的入口（webhook、公開 API、聊天機器人指令）前，先設驗證（密鑰、簽章、白名單）並限制它能觸發的成本。
- **Why**：本章「注意」：webhook 讓公司對外開放，能從外部送訊號的人就能讓代理動起來、觸發成本與動作，啟用前要想清楚誰能按門鈴。
- **How to apply**：Claude 建 n8n webhook、VPS 服務或 Telegram/LINE bot 時，預設加 token 驗證與每日觸發上限，並在回報中寫明誰能觸發。

## (b) 演練候選

### D06-1 寫一個「先檢查再行動」的心跳腳本

- 步驟：
  1. 建 `inbox/` 資料夾與 `heartbeat.py`：每次執行先列出 `inbox/` 中比 `last_run.txt` 新的檔案。
  2. 沒有新檔 → 印「沒事，繼續睡」並結束；有新檔 → 才呼叫 `claude -p "摘要這個檔案"` 並把結果寫到 `outbox/`，更新 `last_run.txt`。
  3. 用迴圈每 60 秒跑一次（或 Windows 工作排程器），中途丟一個檔進 `inbox/`。
- 預期結果：大多數心跳只印「沒事」、不花模型呼叫；只有放檔那一拍才行動——體驗「常跳動、少行動」。

### D06-2 三種觸發一次看懂

- 步驟：用同一個 `handle()` 函式接三種觸發：(1) 時間——迴圈每 N 秒；(2) 內部事件——任務 A 完成時寫 `done-A.flag`，偵測到就啟動任務 B；(3) 外部訊號——`python -m http.server` 改寫的小服務收到 POST（帶正確 token 才接受）就觸發。
- 預期結果：看到研究員→寫手的交接鏈與外部門鈴；故意送錯 token，確認被拒。

### D06-3 估算心跳成本

- 步驟：列出自己想設的 3 個例行，填表「頻率／每月次數／每次是否呼叫模型」，再把每個頻率放慢一級重算。
- 預期結果：直觀看到每月呼叫次數差距，驗證「節奏紀律是預算紀律的姊妹」。
