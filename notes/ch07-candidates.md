# 第 7 章 候選規則與演練（治理、預算與成本控制）

來源：page_0027～page_0030

## (a) 規則候選

### R07-1 長時程／自動化工作開跑前先設預算上限（80% 警告、100% 停止）

- **規則一句話**：任何會反覆呼叫模型的長時程工作（工廠、pipeline、批次），開跑前先定「次數或時間或金額」上限，到 80% 回報、到 100% 自動停止。
- **Why**：本章「有硬性停止點的預算」：80% 警告、100% 自動停止是對抗失控迴圈最有效的保險；「注意」框也說最常見的昂貴錯誤是不設上限「看看會怎樣」。
- **How to apply**：主 Claude 派長時程工作時在完成定義寫明上限（例：最多 N 輪／N 小時）；巡視時到 80% 主動告知使用者，到 100% 停下，不自行續跑。

### R07-2 解除上限必須是明確且留紀錄的決定

- **規則一句話**：已觸發停止的工作，只有使用者明確同意才能延長或解除，並把決定（誰、何時、為什麼、新上限）寫進看板。
- **Why**：本章「董事會」否決權：推翻硬性停止「不是隨手為之，而是明確且被記錄的動作」，解除的人要為此負責。
- **How to apply**：Claude 遇到預算／時間上限觸發時，用 AskUserQuestion 請使用者選「延長多少／停止」，結果寫進 `supervisor-board.md`。

### R07-3 有後果的動作走核准閘門

- **規則一句話**：寄信給他人、發文、付款、刪除資料、對外送出求職訊息等有後果的動作，先給使用者看內容並取得明確同意才執行。
- **Why**：本章「核准與董事會」：某些動作代理不能直接執行，必須送簽核；「一談到責任，沒有人類的公司就是虛構」，核准門檻是內建的人類監督位置。
- **How to apply**：Claude 準備好草稿後停在「待核准」，使用者回「送出」才執行；與既有的「求職送出前要明確同意」規則一致。

### R07-4 模型依任務難度混搭

- **規則一句話**：簡單、大量的步驟用便宜模型（haiku），少數吃重的推理才用強模型。
- **Why**：本章「帳單真正取決於什麼」：模型選擇是常被低估的成本因素，價差可達十倍以上，每個瑣碎例行都用最貴模型等於燒錢；聰明做法是混搭。
- **How to apply**：主 Claude 派子代理時，搜尋／比價／查狀態指定 `model: haiku`，寫程式與研究用預設，規劃與驗證用最強模型；寫自動化腳本呼叫 API 時預設 Haiku。

## (b) 演練候選

### D07-1 做一個有 80%／100% 門檻的預算守門員

- 步驟：
  1. 寫 `budget_guard.py`：讀 `budget.json`（`{"limit": 10, "used": 0}`），每執行一次任務 `used += 1`。
  2. `used >= 0.8 * limit` 時印「警告：預算剩 20%」；`used >= limit` 時拒絕執行並印「硬性停止」。
  3. 加一個 `--override "<理由>"` 參數：只有帶理由才能把 limit 調高，並把時間＋理由追加到 `audit.log`。
  4. 連跑 12 次觀察三段行為，再用 override 解除一次。
- 預期結果：第 8 次出現警告、第 10 次之後被擋；override 後 `audit.log` 留下紀錄——對應「80% 響鈴、100% 撞牆、董事會簽名才能拆牆」。

### D07-2 讀自己的稽核日誌

- 步驟：挑一個既有的自動流程（例：排程腳本的 log 或 `git log`），列出最近一週「有後果的事件」（寄信、push、刪檔），回答「為什麼這件事會發生、是誰（哪個流程）觸發的」。
- 預期結果：找出至少一件無法從 log 回答的事件，補上記錄欄位——體會「日誌只有在有人看的時候才有用」。

### D07-3 帳單四因素試算

- 步驟：為一個假想 AI 公司填表：代理數、每日心跳次數、每次平均 token、模型單價（從官方價目表查），分別試算「全用頂級模型」與「90% 便宜模型＋10% 頂級模型」兩種配置。
- 預期結果：看到兩種配置的月成本差距數倍，驗證「混搭比到處用頂級模型划算」。
